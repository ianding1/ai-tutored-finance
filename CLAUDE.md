# AI-Tutored Finance

A static course website. Lessons are MDX pages with interactive figures. The site never calls an AI:
for grading and explanations it builds a prompt that the learner copies into their own assistant.
All content is AI-generated; the site says so on every page and in every prompt.

## Languages

All languages have the same status; no language is the source of the others. The languages are
listed in `src/i18n/languages.json` (currently `en` and `zh-cn`). A language code is used as the page
folder (`src/content/docs/<code>/`), the URL prefix, the key of text in YAML files (`title: { en: ..., zh-cn: ... }`),
the locale module (`src/i18n/locales/<code>.ts`) and the key in widget label tables. No other code
names a language; to add one, follow "Adding a language" in README.md. `default` in
`languages.json` is only the fallback for visitors whose browser language matches none of the
languages; the site root sends each visitor to the language of their browser.

## Layout

| Path | What it is |
| --- | --- |
| `course/curriculum.yaml` | Lesson order, ids, slugs, titles, summaries, `published`, `introduces`, `uses`. Single source of truth for order. |
| `course/concepts.yaml` | Concept registry: where each concept is defined and its canonical term in each language. |
| `course/keys/<id>.yaml` | Questions, reference answers, rubrics, common errors and lesson context for one lesson. Shown to learners only inside grading prompts. Context items are tagged with `concepts` or `questions`, and common errors with `questions`, so that a grading prompt contains only what concerns the questions being graded. |
| `course/verify/<id>.py` | Recomputes every numeric answer in the key file. |
| `course/widgets.yaml` | Slider ranges of interactive figures. |
| `course/translation-lock.json` | Hash of every language version of every page and text field, taken when the versions were last in sync. Generated by `npm run i18n:lock`. |
| `src/content/docs/<code>/` | Pages of one language. Every page exists in every language with the same file name. |
| `src/i18n/` | `languages.json`, shared types and one locale module per language (UI strings and prompt templates). |
| `src/pages/index.astro` | Site root: sends visitors to the language of their browser. |
| `src/components/` | `Ref`, `Def`, `Figure`, `Check`, `CheckAll`, `Exercises`, `Quiz`, `widgets/*`; `overrides/` replaces Starlight parts (content wrapper, footer, sidebar with lesson status, previous / next links). |
| `src/scripts/` | Browser code: prompt building, learning progress (localStorage), lesson status, selection "Explain this". |
| `scripts/check.py` | Blocking consistency checks (CI). |
| `.github/review-rules.md` | Rules for the advisory AI review of pull requests. |

## Commands

```bash
npm install
npm run dev          # local preview at http://localhost:4321/ai-tutored-finance/
npm run build        # production build; fails on bad LaTeX or unknown question/reference ids
npm run check        # python3 scripts/check.py (needs PyYAML)
npm run i18n:lock    # after all language versions are in sync again, record their hashes
```

Versions are pinned to Astro 5.12 and Starlight 0.34. Astro 7 replaced the Markdown pipeline
(Sätteri instead of remark/rehype), which affects `remark-math`, `rehype-katex` and
`src/plugins/remark-heading-id.mjs`. Upgrade in a separate pull request.

## Publishing a lesson from a lesson plan

The author writes private lesson plans elsewhere (currently in Chinese). A plan contains notes about
one learner, revision history and answers inline. To publish a finished lesson:

1. Add or update the lesson in `course/curriculum.yaml`: `summary`, `published: true`, `introduces`, `uses`.
2. Add every new concept to `course/concepts.yaml` (`defined_in`, the canonical term in every language, `short`).
3. Write `src/content/docs/<code>/lessons/<slug>.mdx` in the language of the plan, for a general reader:
   - remove everything about a specific learner. A mistake one learner made is not a "key point"
     or a "note" for everyone; keep it only if it is a common misconception, and then put it in
     `common_errors` rather than in the text;
   - the text, figure captions and summary never state the answer to a check question or an
     exercise, and no question only asks the learner to repeat an argument the text already makes.
     When an important result can be derived by the learner, the text sets up the question and
     points to the exercise (`<Ref check="Q1" />`) instead of giving the derivation;
   - leave out the learning goals and the review part of the plan; the page starts with the first section;
   - every `##` heading gets a stable id: `## Diversification [#diversification]`;
   - mark each concept definition with `<Def id="...">canonical term</Def>`;
   - every reference to a lesson, section, figure, question or concept uses `<Ref ... />`;
   - figures: `<Figure id="6-1" title="..." observe="...">` around a widget component.
4. Move questions, answers, rubrics and common errors into `course/keys/<id>.yaml`. Tag each
   context item with the `concepts` or `questions` it serves (leave both out only for facts every
   question needs), and each common error with its `questions`. Any fact a question needs from the
   lesson (example data, figure parameters) must be in a context item tagged for that question.
   Place `<Check id="..."/>` in the right section and `<Exercises />` at the end. Every lesson
   answers its check questions on the page; `<CheckAll />` (check questions graded by prompt) is no
   longer used by any lesson.
   Check questions are answered on the page:
   - each is one true / false statement (`correct: true` or `false`, no `choices`) or one
     multiple-choice question (`choices`: a list of options, `correct`: the letter), about one core
     point of the section it follows;
   - they test qualitative conclusions: direction, conditions, mechanism, whether a claim holds. A
     number may appear, but the answer must follow from understanding, not from working through a
     calculation. A figure-based check question asks about a direction or pattern in the figure, not
     a precise reading;
   - the learner picks an answer and submits it; the page says at once whether it is right. A wrong
     answer never reveals the right one, so the learner can think again: each wrong option of a
     multiple-choice question has `why` (what is wrong with that option), and a true / false question
     has `hint` (what to think about, without the verdict). `answer` holds the full explanation for
     reference and is not shown;
   - they have no `expected` and no `rubric`.
   Exercises:
   - they hold the calculations, derivations and applications, without many parts; when a question
     has many parts, drop the ones that only plug numbers into a formula and keep the ones that need
     the formula to be understood or used flexibly. A number that is only a stepping stone can be
     given in the question;
   - a point tested by a check question is never tested again in the same or nearly the same way. It
     may appear only as a step in something larger: combining points from different sections, a new
     situation or decision, a derivation the text leaves out, or the limits of a result. Test: would
     a learner who answered every check question correctly learn something new from the exercise?
   - each exercise targets a named misconception, recorded in a `common_errors` entry tagged with
     its question. A learner who only repeats the steps of the text does not get "ok";
   - ask of every part: "can it be answered by recalling an example from the lesson or redoing the
     text's procedure?" If so, rework it (change the situation, the known facts or the goal of the
     decision) or keep it as a short step inside a larger part;
   - each lesson has at least one exercise that evaluates a plausible but wrong claim (a colleague,
     an analyst or an advertisement says ...): the learner judges it, finds where it fails and, where
     useful, under which conditions it would hold;
   - where it fits, a part asks whether a result makes sense: compare it with economic common sense,
     a limiting case or an order of magnitude;
   - no part only asks the learner to repeat an argument the text already makes;
   - exercises may give a formula as a hint; they have no points;
   - exercises stay within the lesson and the lessons just before it. Mixing stages is left to the
     quizzes.
5. Put every numeric answer in `expected` and recompute it in `course/verify/<id>.py`.
6. Write the page and every text field in each of the other languages. Formulas, heading ids and
   components must be identical. English uses plain, standard English without idioms.
7. Run `npm run check`, then `npm run i18n:lock`, then `npm run build`.

## Rules that check.py enforces

- Every page and text field exists in every language of `src/i18n/languages.json`.
- Translation lock: if some language versions of a page or text field changed since the last
  `npm run i18n:lock` and others did not, the check names the languages that still need the change.
- All language versions of a page have the same heading ids, the same components with the same
  attributes in the same order, and the same formulas.
- Every language has a locale module with every UI string, and every widget label table has an
  entry for every language.
- No plain-text references such as "（0.4）", "见 4.5", "第 6 段", "question 4". Use `<Ref>` in MDX
  and `[[0.4]]`, `[[0.3#sec]]`, `[[concept:id]]`, `[[check:Q4]]`, `[[fig:6-1]]` in YAML text.
- References point to things that exist. Sections, figures and questions can only be referenced in
  published lessons.
- `uses` concepts come from earlier lessons; questions only test concepts taught so far; `<Def>` ids equal `introduces` and use the canonical term.
- Every check question appears exactly once, in the section named by its `section` field.
- `expected` values match `course/verify/` and appear in every language's answer text.
- Slider values named in questions are reachable; slider attributes match `course/widgets.yaml`.
- No private teaching notes (学员, 教案, 修订记录, briefing) in published content.
- Context items and common errors in key files refer to existing concepts and questions.
- A lesson with check questions graded by prompt (no `correct`) contains `<CheckAll />` exactly once,
  a lesson whose check questions are all answered on the page has no `<CheckAll />`, and a lesson with
  exercises contains `<Exercises />` exactly once.
- A check question answered on the page has `correct` (true / false, or a letter of `choices`), has
  2 to 8 options if it has `choices`, a `why` on every wrong option (none on the right one) or a
  `hint` if it is true / false, and no `expected` and no `rubric`.
- No question has `points`, no rubric mentions points or partial credit, and no quiz question or
  quiz page mentions points.
- Chinese text (every `zh-*` language) uses Chinese quotation marks and the word 提示词 (提示詞 in
  Traditional Chinese), has no space after full-width
  punctuation, and never ends a bold run with full-width punctuation directly before a character
  (write `**……正负**。` instead of `**……正负。**`, which Markdown does not render as bold).
- Every prompt template of every language includes that language's AI-generated-content disclaimer.

## Terms

| zh-cn | en | `kind` / component |
| --- | --- | --- |
| 随堂题 | check question | `check`, `<Check>`, answered on the page |
| 练习题 | exercise | `exercise`, `<Exercises>` |
| 综合测验 | comprehensive quiz | `quiz`, `<Quiz>` on the page `lessons/t<n>-quiz.mdx` (`T1`, `T2`, `T3`) |

No question is scored: every result is "ok" or "revise".

## Prompts

- The site stores only learning progress: the latest result ("ok" / "revise") of each submitted
  question, in localStorage. It stores nothing else about the learner (no background, preferences,
  concept status or notes), has no progress page and no review feature, and no prompt contains
  anything about the learner.
- The sidebar shows one status mark per lesson: an empty ring (no question submitted), a half-filled
  ring (some submitted), a filled ring (all submitted, including questions that need revision).
  There is no separate course outline page and no "how to use" page: the interface must explain
  itself through its labels and short hints next to the controls.
- Check questions are true / false or multiple choice and are answered on the page: each has its own
  submit button, the result ("ok" / "revise") is shown and stored at once, and a wrong answer shows
  what is wrong with the chosen option (or a hint) without revealing the right answer.
- Other answers are not entered on the site. Exercises are submitted together by `<Exercises />`.
  The prompt ends with an empty "learner's answers" heading; the learner attaches a photo or types the
  answers after it.
- Check questions (随堂题), exercises (练习题) and comprehensive quizzes (综合测验, `T1`–`T3` in the curriculum)
  are reviewed without scores: the result marks each question "ok" or "revise". All of them use the
  same feedback prompt. Results saved with scores by earlier versions of the site become "ok" (full
  marks) or "revise".
- Each question shows its latest result next to its label ("not answered", "OK", "needs revision").
  There is no progress summary under the submit buttons.
- Learners may submit only some questions. The grader grades only the answered ones and lists only
  those in the result block; other questions keep their earlier result or stay "not answered".
- Buttons copy the prompt directly to the clipboard. The dialog is only a fallback.
- Explanation prompts contain the selected text, its paragraph, its section and the lesson context.
- The wording of each prompt is in the locale module of its language; `src/scripts/prompts.ts` adds
  the parts that do not depend on the language (the result block, lists and quoting).

## Writing a quiz

The course has three comprehensive quizzes, each after a block of consecutive stages: `T1` after
Stage 2 (Stages 0–2), `T2` after Stage 4 (Stages 3–4) and `T3` after Stage 6 (Stages 5–6). Stage 7
(the capstone) has no quiz. A quiz may use every earlier stage but mainly tests its own block, and
it does not try to cover every lesson: covering lessons is the job of check questions and exercises.

Style: understanding and modeling first, little calculation.

- Each problem is a situation (a firm, a household, an investor, a piece of news, a policy), not a
  topic. The stem does not name the concept, formula or lesson to use, and it may contain facts that
  turn out not to matter. The learner must recognize which concepts apply, build a simple model
  from the description (for example, see that a payment rising with inflation is a growing
  perpetuity discounted at a real rate) and draw the conclusion.
- Most problems combine lessons from at least two stages; a problem that one lesson's exercises
  could ask is not a quiz problem.
- Difficulty never comes from harder mathematics: no long derivations, no algebra for its own sake,
  no numbers chosen to make the arithmetic hard. Mathematics the model needs (a present value, a
  derivative, a variance) is fine.

Quizzes also follow the exam rules in the author's curriculum ("阶段考试"):

- A question shows whether the learner understands the financial concept, not whether they can run a
  familiar procedure: its meaning, the conditions under which a result holds, the mechanism behind it,
  its use in an unfamiliar but relevant situation, and whether a result makes sense. Difficulty comes
  from the depth of understanding needed, not from extra calculations, several tasks or artificially
  complicated conditions. Each question names the misconception it can reveal (in `common_errors`);
  a learner who only applies the steps does not get "ok". Routine calculation is a small part of the
  quiz (at most about one part in seven).
- Each question has its own core point; basic concepts used along the way may repeat.
- Each part asks one core question. It may ask to compute and then explain when the explanation
  follows from that computation, but it never combines unrelated computations or several separate
  questions. Difficulty comes from the depth of that one question, not from the number of questions.
- Only lessons of the block and earlier stages; the questions carry no lesson or difficulty labels and no
  hints. The page starts with instructions and a formula sheet.
- Part 1 is true / false with reasons (both verdicts occur; no "uncertain") (`part: judge`); a verdict without a reason needs
  revision. Part 2 holds problems (`part: problem`).
- Calculation questions require working. Rubrics say, for each part, what an "ok" answer contains
  and which errors need revision; a small slip that does not change the reasoning is pointed out but
  does not need revision.
- Exercises and quizzes divide the work: exercises practise one lesson; quizzes mix lessons and
  stages without saying where a question comes from, use less calculation, and ask more often which
  concept applies and under which conditions. Before adding a quiz question, check the exercises of
  the lessons it uses for the same insight (for example, a quiz question and exercise Q2 of lesson 3.4 that both
  ask why a perpetuity is not infinitely sensitive to rates); if one exists, change the question so
  that it needs something the exercise does not.
- For each question, ask "can it be answered by recalling an example from a lesson?" and rework it
  if so, for example by changing the situation, the known facts or the goal of the decision. Adapting
  an exercise with a new extension is fine.
- Every numeric answer is in `expected` and recomputed in `course/verify/E<n>.py`.
- The site's quizzes are for every learner; do not target one learner's weak points.

## Writing conventions

- In languages other than English, technical terms get the English term in parentheses on first use.
- All formulas use LaTeX. Write currency as "12,000 美元" / "12,000 dollars" rather than with `$`.
- Calculations in percentage points; variance in %².
- Facts that change over time (tax rates, limits, rates) state the year and source.
- Never tell the reader to buy or sell a specific security.
- Code, comments, scripts, check messages and developer documentation are in English; only course
  content and UI text are multilingual.
- Chinese typography lives in `src/styles/custom.css` ("Chinese typography", `:lang(zh)`): CJK fonts for
  quotation marks, smaller headings, justified text, math at 1.1em, no text below 14px.
- Numeric table columns are right-aligned (`---:`). Tables are three-line tables (三线表: top rule,
  rule below the header, bottom rule) and only as wide as their content.
- Use one separator per block: whitespace, a background or a border, not two. Figures have no frame
  (whitespace and caption only); question blocks have a background and no border.
- Widgets fit the page width: each draws a wide SVG (`viz-wide`, 640 wide) and a narrow one for
  phones (`viz-narrow`, 360 wide, same font sizes); a container query on the figure shows one.
  Long LaTeX formulas may overflow; the page itself must not scroll sideways.
- Text uses the system font smoothing (not `antialiased`) and body text one step stronger than
  Starlight's default (`--sl-color-text: var(--sl-color-gray-1)`).
